# KP-005: 流控配额修改必须评估对高频日志场景的影响

## 严重级别
major

## 来源
流控配额调低后系统服务关键日志静默丢失，问题排查困难

**问题详情**：
- 严重级别：严重（Major）
- 影响范围：高频打印日志的系统服务
- 出现概率：高频日志场景下必现
- 故障恢复：调回配额后恢复，但已丢失的日志不可追溯

## 问题回顾
为降低 hilogd 的 CPU 占用，将 domain 级流控默认配额从 51200 字节/秒下调到 10240 字节/秒。修改后，某系统服务在高负载场景下的关键错误日志被静默丢弃（domain 流控默认关闭，但该产品在出厂时开启了 `hilog.flowctrl.domain.on=true`）。由于 `LOGLIMITD` 提示日志只在周期结束时才输出一条，开发人员在排查问题时未注意到流控提示，误判为服务未产生日志，浪费了大量排查时间。

## 代码陷阱模式

**陷阱：修改流控配额（`DEFAULT_QUOTA`）、周期或丢弃策略，未评估对已有高频日志场景的影响。**

此陷阱的隐蔽性在于：
1. 低频日志场景下修改无感知（配额从未用满）
2. 日志丢弃是静默的，只在周期结束时输出一条 `LOGLIMIT` / `LOGLIMITD` 提示
3. 提示日志可能被其他日志淹没，开发人员不易注意到
4. 产品出厂配置可能与代码默认值不同（如产品开启了默认关闭的流控开关）

## 高风险代码区域

### 1. 进程级流控配额
- **文件**: `frameworks/libhilog/param/properties.cpp`（`DEFAULT_QUOTA = 51200`，行 72）
- 默认配额 50KB/秒，通过 `hilog.quota.proc.<进程名>` 系统参数可覆盖
- **文件**: `frameworks/libhilog/hilog_printf.cpp`（`HiLogFlowCtrlProcess`，行 178-208）
- 使用原子变量 `processQuota`、`gSumLen`、`gDropped`，1 秒周期窗口

### 2. domain 级流控配额
- **文件**: `frameworks/libhilog/param/properties.cpp`（`GetDomainQuota`）
- 通过 `hilog.quota.domain.<hex>` 系统参数读取，无代码级默认值
- **文件**: `services/hilogd/flow_control.cpp`（`FlowCtrlDomain`，行 43-78）
- `DomainInfo` 结构含 `quota`、`sumLen`、`dropped`，1 秒周期

### 3. 流控开关
- **文件**: `services/hilogd/etc/hilog.para`
- `hilog.flowctrl.proc.on=false`（进程流控默认关闭）
- `hilog.flowctrl.domain.on=false`（domain 流控默认关闭）
- 产品可能在出厂配置中修改这些默认值

### 4. 超限提示日志
- **进程级**：`hilog_printf.cpp` 中插入 tag 为 `LOGLIMIT` 的日志
- **domain 级**：`log_collector.cpp` 的 `InsertDropInfo` 插入 tag 为 `LOGLIMITD` 的日志
- 提示日志只在周期结束时输出一次，包含上一周期的丢弃计数

### 5. 流控开关切换
- **文件**: `services/hilogd/service_controller.cpp`（`HandleDomainFlowCtrlRqst`，行 811-820）
- 通过 `DOMAIN_FLOWCTRL_RQST` 命令切换
- **文件**: `frameworks/libhilog/param/properties.cpp`（`SetProcessSwitchOn`）
- 通过系统参数切换

## 检查规则

修改流控配额、周期或丢弃策略时，必须执行以下步骤：

### Step 1: 搜索流控相关代码
```bash
grep -rn "FlowCtrl\|DEFAULT_QUOTA\|quota\|gSumLen\|gDropped\|LOGLIMIT\|flowctrl" --include="*.cpp" --include="*.h" --include="*.c"
```

### Step 2: 评估配额修改影响
对每个修改，回答：
1. 修改的配额是否影响进程级流控、domain 级流控，还是两者？
2. 高频日志场景（如系统启动、性能压测、异常风暴）下配额是否足够？
3. 流控默认关闭时，修改是否影响已有配置（产品可能已开启流控）？
4. 超限提示日志的频率和可见性是否足够让开发人员注意到？

### Step 3: 场景化验证
修改后必须覆盖以下场景：
1. **低频场景**：少量日志打印，确认不受流控影响
2. **高频场景**：大量日志打印（超过配额），确认丢弃行为正确
3. **周期边界**：日志打印跨周期，确认周期重置和 `sumLen` 清零
4. **提示可见性**：确认 `LOGLIMIT` / `LOGLIMITD` 提示日志正确输出且可被检索
5. **开关切换**：确认 `hilog -Q pidon/pidoff/domainon/domainoff` 正确切换

## 正确模式

```cpp
// 正确：修改配额时增加配置化能力，保留默认值不变
constexpr int32_t DEFAULT_QUOTA = 51200;  // 保持默认值不变

int32_t GetProcessQuota(const std::string& procName)
{
    // 优先从系统参数读取，回退到默认值
    auto cached = procQuotaCache.getValue();
    if (cached.has_value()) {
        return cached.value();
    }
    return DEFAULT_QUOTA;  // 系统参数未设置时使用默认值
}
```

## 反面模式

```cpp
// 错误：直接修改默认配额，不考虑已有场景
constexpr int32_t DEFAULT_QUOTA = 10240;  // 从 51200 下调到 10240
// 高频日志场景下大量日志被静默丢弃，关键错误日志丢失
// 产品出厂时开启了流控开关，影响所有产品
```

## 关联风险：debug 应用跳过流控

`HiLogFlowCtrlProcess` 在 `IsDebuggableHap()` 或 `IsDebugOn()` 时跳过进程级流控。修改流控逻辑时不要改变 debug 应用的跳过行为，否则会影响调试体验。domain 级流控不跳过任何类型（包括 `LOG_APP` 也不走 domain 流控，因为 `FlowCtrlDomain` 在 `msg.type == LOG_APP` 时直接返回 `FLOW_CTL_NORAML`）。
